## 2. What was built

### WP1 — Safe terminal and command execution
- `src/execution/service.ts` (new): bounded in-memory execution history (50 records),
  statuses `running|succeeded|failed|cancelled|timed-out`, linked cancellation
  (per-execution `cancel(id)`, `cancelAll()`, linked external `AbortSignal`),
  per-run timeout, bounded output, duplicate-invocation refusal while identical
  invocations run in the same directory, task association (`taskId`), diagnostics
  and test-count attachment, and listener notifications for the webview.
- `src/agent/runtime.ts`: orchestrator validation path now records through the
  same service with `taskId` (signature extended in `orchestrator.ts` to accept
  an optional `taskId`; backward compatible for other callers).
- `src/agent/commandTools.ts`: optional `executionService`; when present every
  approved run is recorded; when absent behavior is unchanged (existing tests pass).

### WP2 — Build-system adapters
- `src/build/types.ts`, `src/build/adapters.ts`, `src/build/toolchain.ts` (new):
  common `BuildAdapter` interface implemented by **22 adapters**: Karkain (`.kark`/
  `karkain.toml`), Maven, Gradle, npm, pnpm, yarn, pip, Poetry, uv, Hatch, Go,
  Cargo, CMake, Make, Ninja, dotnet, MSBuild, Composer, Bundler, Dart, Flutter, Swift.
- Detection is local and path-based with manifest-content confirmation.
- Toolchain probing uses the same fail-closed, no-shell rules as the command
  runner; missing executables are reported unavailable (never guessed).
- Multi-step adapters (CMake) stop at the first failing step.

### WP3 — Test execution
- `src/build/testOutput.ts` (new): conservative parsers for JUnit/Surefire/Gradle,
  pytest, mocha/jest/vitest, `go test`, `cargo test`, `dotnet test`, CTest, RSpec,
  PHPUnit, Dart/Flutter, Swift and Karkain PASS/FAIL output.
- Counts are `undefined` when ambiguous; failure locations extracted when encoded.

### WP4 — Diagnostics
- `src/diagnostics/sourceDiagnostics.ts` (new): `file:line:column` extraction for
  TypeScript, Java/Maven, C/C++ (gcc/clang), Go, Rust (header + `-->` location),
  Python tracebacks, Karkain-format diagnostics; feeds the existing
  diagnose → propose → approve → apply → revalidate loop.

### WP5 — Debugging/repair loop
- Demonstrated (not just implemented): isolated project with an intentionally
  broken function → agent detects build system → runs failing tests (approval
  logged) → reads source → approved change applied → re-runs tests → **3 passing**,
  verified on disk and in history. Bounded repair via existing agent controls.

### WP6 — Karkain compiler integration
- `src/build/adapters.ts` (Karkain adapter): detects `karkain.toml`/`.kark`,
  generates `karkain build <entry>` from the detected entry point, probes
  `karkain --version` (REAL, works), runs `karkain test`.
- **Environment truth**: the real Karkain compiler **cannot execute on this
  machine** — `karkain.exe check main.kark` exits with code 3 and no diagnostics
  even on known-good conformance files; `karkain.exe check` reports "cannot
  locate src/compiler to build the self-hosted engine (set KARKAIN_KCC)";
  `kcc.exe` fails to launch (missing DLL). Tests therefore use a controllable
  fixture compiler (`test/fixtures/karkain-toolkit/karkain.bat`) implementing
  the documented CLI contract and exit codes (0/2/3/4). Real-vs-fixture evidence
  is clearly separated in `scripts/demo-build-tools.cjs` and in all reports.
- No Karkain flags or capabilities were invented; adapter commands map to the
  verified CLI documented in the Karkain repo (`check|build|test|lint`, exit
  codes per `pkg/cli/exitcodes.go`).

### WP7 — UI integration (existing webview)
- `src/chat/protocol.ts`: `execution` and `executionHistory` messages, `ExecutionView`.
- `src/chat/chatViewProvider.ts`: runtime execution subscription posts execution
  updates and an execution history on view ready; diagnostics and test counts ride
  along on the record.
- `media/chat.js`: execution cards with status badges (Running/Passed/Failed/
  Cancelled/Timed out), command, cwd, duration, exit code, test counts, diagnostic
  count, output in a scrollable pre, truncation/timeout/cancellation warnings.
  Cards update in place by `data-execution-id`.
- `media/chat.css`: execution card, badge and output styles.

### WP8 — Reliability, security, performance
- Process cleanup: existing runner kills with SIGTERM then SIGKILL (2 s); verified
  timeout (659 ms) and cancel cases in unit tests.
- Cancellation: linked external signal, `cancel(id)`, `cancelAll()` — unit tested.
- Bounded output: existing 120 k char cap + redaction; history capped at 50 records.
- Long-running: monitored via execution records; timeout terminates.
- Duplicate invocations in one directory refused while one runs (tested).
- Workspace boundary: existing realpath containment; approvals enforce the model.
- Malformed output: parsers return `undefined` counts; nothing fabricated.
- Execution state is in-memory and lost on reload (documented limitation).

## 8. Remaining limitations (explicit)

1. **The real Karkain compiler cannot run in this environment**; Karkain build/
   check/test paths are exercised against a fixture compiler implementing the
   documented contract. Real-compiler end-to-end verification is NOT claimed.
2. Java builds need Maven/Gradle installed; the Java toolchain here is absent
   (`mvn` unavailable, Gradle present but not exercised end-to-end).
3. Diagnostics are pattern-matched; they can miss or misattribute locations.
4. Execution history is in-memory (bounded, lost on reload).
5. Multi-root workspaces and per-command working directory are not supported.
6. CMake test output is the only CTest path exercised; C/C++ toolchain is absent
   in this machine's PATH (cmake/make present, gcc absent).
7. Karkain diagnostics use the unverified `file:line:col` format (documented as
   heuristic); no stable machine-readable Karkain diagnostic format exists.
8. Packaged VSIX tests were not re-run; release remains unpublished and untagged
   per task restrictions.
