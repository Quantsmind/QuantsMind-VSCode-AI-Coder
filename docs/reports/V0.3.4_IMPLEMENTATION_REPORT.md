## 1. Executive summary

v0.3.4 makes conversation history and attached-file context reliable, visible and honest.

The four defects this release closes:

1. **Invisible replayed history.** A restored transcript was silently replayed to the provider. The user could not tell whether a reply was caused by the message they just typed or by an old conversation that had been loaded back. This was the confirmed root cause of the v0.3.0 "generic reply" investigation (`messages=19 chars=4359` = a 17-turn restored transcript + system prompt + a 25-character question).
2. **Provider-history vs persisted-transcript divergence.** The provider received `<attached_context>` blocks for historical turns, but the persisted transcript stored only attachment *path labels*. After a reload the exact supplied context could not be reconstructed, so a replayed turn was **not** the turn that was originally sent.
3. **Ambiguous attachment status.** The UI could show a paperclip for a file whose captured content was no longer available, implying content that was never sent.
4. **Unsafe destructive operations.** Clearing a conversation touched global state without a confirmation and without a guarantee that sibling conversations were untouched.

What was implemented:

- A **provider-history state model** that is derived from the messages actually handed to the provider (`ChatSession`), not from what the UI rendered, and is re-measured after every turn.
- **Verbatim attachment capture** (`src/chat/attachmentContext.ts`): each user turn stores the redacted context blocks it was sent with, plus a SHA-256 checksum, character count and redaction count, under per-message and per-conversation budgets with oldest-first release.
- **Exact replay reconstruction**: restored turns are rebuilt through the same `buildUserContent()` the live turn used, so the restored provider request is byte-identical to the original.
- A **read-only freshness audit** that compares stored captures against the files on disk and warns on drift — and never substitutes current file contents for the captured context.
- **Schema-v2 persistence** with non-destructive, backward-compatible migration and an unreadable-record salvage key, so a partially written or malformed store cannot erase user data.
- **Conversation management UX**: history status line, per-request context strip, Clear (this conversation only) and Restore, all destructive paths behind a native modal confirmation.
- **Sanitized request diagnostics**: two log lines carrying sizes, counts, ids, timing and finish reason only — never prompt text, attachment content, credentials or headers.

Verification: `npm run verify` exits 0 end-to-end — lint clean, dependency guard clean, **376 unit tests passing**, **34 integration tests passing**, packaging clean, VSIX checks passing, **4 packaged-extension tests passing**, clean-install verification reporting `quantsmind.quantsmind-vscode-ai-coder@0.3.4`. All seven Campaign-6 provider prompt regression tests are preserved and passing.

No security control was weakened; no credential handling changed; no user data was migrated destructively.

## 4. Baseline inspection

Baseline facts that shaped the design:

- `ConversationStore` persisted `StoredMessage { role, text, attachments: string[], createdAt }` — `attachments` was **path labels only**. The provider-bound `ChatSession` was rebuilt from those labels, so `<attached_context>` could not be reproduced.
- `ChatSession.load()` replaces history wholesale, which makes restore idempotent — good; but nothing told the UI how many turns had been loaded or how many characters they cost.
- `buildMessages()` puts `[system, …history, user]`. Nothing measured that split, so a 4 KB replayed history and a 25-character question were indistinguishable in the logs.
- `ConversationStore.clear(id)` already scoped clearing to one conversation, but no UI action or confirmation existed.
- `Logger` prefixes an ISO timestamp on every line and runs `redactSecrets()` on each line — that satisfies "request timestamp" and "never log keys" without new code.
- Unit tests run in plain mocha and cannot import `vscode`-dependent modules. That is why the new logic lives in two dependency-free modules, `attachmentContext.ts` and `requestMetrics.ts`.

## 6. Conversation history implementation (assignment §3 — A)

**History visibility reflects the messages actually sent, not what the UI rendered.**

- `refreshHistoryState(conversation, source)` — [chatViewProvider.ts:363](file:///F:/Codes/Git/Quantsmind-Products/QuantsMind-VSCode-AI-Coder/src/chat/chatViewProvider.ts#L363) — derives counts and character totals from `ChatSession`, the object that is passed to `buildMessages()`, so the numbers are the provider's numbers. It is invoked on load, on restore-after-reload (`source === 'reload'`), on conversation switch (`'switch'`) and after every assistant turn.
- `refreshHistoryCounts()` — [chatViewProvider.ts:503](file:///F:/Codes/Git/Quantsmind-Products/QuantsMind-VSCode-AI-Coder/src/chat/chatViewProvider.ts#L503) — recomputed inside `recordAssistant()` whenever the turn is added to the session, then posted with `postHistory()`. The count therefore tracks the live session even if a save is still in flight.
- The four categories are distinguished explicitly, both in the webview strip and in the log line: **system instructions** (`systemChars`), **replayed history** (`historyMessages` / `historyChars`, measured as everything except the newest message), **the current prompt** (`promptChars`) and **attached file context** (`attachmentItems` / `attachmentChars`).
- **Local-only messages** (`localOnly: true`, e.g. the workspace summary) are stored for the UI but excluded from provider replay by `providerContentFor()` — [attachmentContext.ts:233](file:///F:/Codes/Git/Quantsmind-Products/QuantsMind-VSCode-AI-Coder/src/chat/attachmentContext.ts#L233) — and rendered as "QuantsMind · local only" in the transcript.
- **New Chat starts clean.** `startNewChat()` resets `ChatSession`, replaces the conversation, and sets `history = { ...EMPTY_HISTORY, conversationId }`. The webview then reports "History: clean · starts with your next message".
- **Accidental replay is prevented at two levels.** (a) `syncHistoryBeforeSend()` loads exactly the current conversation's replayable turns before every send, and `ChatSession.load()` replaces rather than appends, so a second send of the same conversation cannot double-count turns. (b) In-flight requests are keyed by `requestSeq`; `switchConversation` (L647) and `clearCurrentConversation` (L688) bump it and every post-send branch checks `requestId === this.requestSeq` ([L1814](file:///F:/Codes/Git/Quantsmind-Products/QuantsMind-VSCode-AI-Coder/src/chat/chatViewProvider.ts#L1814), L1820, L1832, L1854), so a stale reply can neither be recorded nor rendered after New Chat / Clear / Switch. Switching is additionally blocked while a request is in flight.
- **Restored ordering preserved**: `providerHistoryMessages()` replays turns in stored order, skipping empty and local-only turns; the newest user message is appended last by `buildMessages()`.

Verified by integration test "restores a long conversation in order with the new prompt last" (17 restored turns → 19 outbound messages, exactly one `system` message, `messages[18]` is the new prompt, breakdown reports `historyMessages=17`) and "starts clean after New Chat and never replays a restored conversation" (the post-New-Chat request is exactly `[system, {role:'user',content:'Reply with exactly: READY'}]`).

## 7. Attachment persistence implementation (assignment §4 — B)

**The provider-history vs persisted-transcript discrepancy is closed by storing what was sent.**

- `captureAttachments(items, timestamp)` stores, per attachment: `path`, `content` (the already-redacted context the provider received), `chars`, `sha256`, `redactions`, `capturedAt`. Anything above `MAX_ATTACHMENT_CONTEXT_CHARS_PER_MESSAGE` is truncated with an in-content marker and the remainder reported; anything above `MAX_ATTACHMENTS_PER_MESSAGE` (50) is **dropped explicitly and named** to the user — content is never silently lost ([attachmentContext.ts:87](file:///F:/Codes/Git/Quantsmind-Products/QuantsMind-VSCode-AI-Coder/src/chat/attachmentContext.ts#L87)).
- `enforceAttachmentBudget()` applies the conversation-wide 96,000-character budget and releases the **oldest** captured content first, preserving message order, attachment order and the path labels, so a long conversation cannot silently overflow global state ([attachmentContext.ts:266](file:///F:/Codes/Git/Quantsmind-Products/QuantsMind-VSCode-AI-Coder/src/chat/attachmentContext.ts#L266)).
- **prompt ↔ attachment relationship preserved**: the exact question text is stored separately in `message.question` when it differs from the display text, and replay uses `question ?? text` — so a turn displayed as the default-mode question still replays the verbatim prompt that was sent.
- **Equivalent reconstruction**: `providerContentFor()` rebuilds historical turns with the same `buildUserContent()` used live. Proven two ways — unit test "reconstructs the exact provider content of the original turn" asserts string equality of the reconstruction against the original live content, and integration test "replays the captured attachment context after a simulated reload" asserts `extractContext(replay) === extractContext(original)` on the real HTTP body.
- **Honesty about availability**: `displaysForStoredAttachments()` yields `captured` / `unavailable` / `legacy`, and `attachmentRestoreWarnings()` turns those into user-visible notices. A released or empty capture is labelled "its captured contents are not replayed"; the UI never claims content is present when it is not. A released capture is written as `ATTACHMENT_DROPPED_MARKER`, never as stale file text.
- **Deleted / inaccessible / modified files handled safely**: see §8 audit. Reads go through the existing context pipeline, so workspace containment, exclusions, size limits and `redactSecrets()` all still apply to what is stored.
- **No silent substitution of new file contents for old captured context**: the replay path reads only `StoredAttachment.content`. The disk is read exclusively by the *audit*, which is read-only and comparison-only.
- Integration test "warns when a historical attachment no longer matches the file on disk" attaches a file, disposes the provider, rewrites the file on disk, reloads, and asserts (a) a warn notice plus `modified=1` in the log, and (b) that the replayed request still contains the captured `= 42` and **not** the new `= 7`.

## 8. Restoration reliability and the freshness audit (assignment §5 — C)

- **After reload / extension-host restart**: `restoreConversation()` re-loads the active conversation, `ChatSession.load()` replaces history, `refreshHistoryState(..., 'reload')` posts the restored counts, and restore warnings are re-sent after the `init` payload so the webview is guaranteed to receive them.
- **Interrupted-persistence recovery**: `ConversationStore.salvage()` — [persistence.ts:171](file:///F:/Codes/Git/Quantsmind-Products/QuantsMind-VSCode-AI-Coder/src/chat/persistence.ts#L171) — copies every record it could not parse into `quantsmind.chat.conversations.v1.unreadable.v1` **before** the list is rewritten, so a partially written save cannot destroy data, and the raw records remain recoverable.
- **Malformed / partial records**: `parseMessage()` / `parseConversation()` are strict and order-preserving; a bad element is dropped without shifting the surviving messages, and a bad conversation is quarantined instead of crashing the store. Verified by "keeps original message order and rejects malformed records without losing the rest" and "salvages a conversation record that cannot be parsed before rewriting the list".
- **Duplicate-replay protection**: idempotent `load()` + `requestSeq` invalidation + the in-flight switch guard (see §6). The reload test asserts no turn appears twice in the outbound body.
- **Failed writes are surfaced, not swallowed**: `save()` lets a `memento.update()` rejection propagate so the user sees a failure rather than a silently truncated transcript — test "a failed storage write surfaces to the caller instead of silently dropping history".
- **No destructive migration** (see §9).
- **Freshness audit**: `auditAttachmentFreshness()` ([chatViewProvider.ts:415](file:///F:/Codes/Git/Quantsmind-Products/QuantsMind-VSCode-AI-Coder/src/chat/chatViewProvider.ts#L415)) runs after a reload or a switch, audits at most `FRESHNESS_AUDIT_LIMIT = 12` stored, non-selection, unredacted captures, resolves each path through `resolveStoredPath()` (rejects absolute/drifting paths), checks size against `maxFileSizeBytes`, and compares with `freshnessOf()`. It logs `attachment freshness audit conversation=… checked=… unchanged=… modified=… missing=… skipped=…` and posts one warning notice stating that restored requests replay the context captured at the time of each message and that current file contents are not substituted in. It never rewrites stored data and never sends anything to the provider.

## 9. Migration details (assignment §4 requirement "backward-compatible schema migration with tests")

**Non-destructive, additive, backward and forward compatible.**

- Records written before this release carry **no** `schema` field. `parseConversation()` defaults them to `schema: 1` and reads them successfully; nothing is rejected or rewritten on first read.
- Any write through `toRecord()` stamps `schema: CONVERSATION_SCHEMA_VERSION` (2). `Conversation` therefore declares `schema?: number` — absent means pre-v0.3.4 ([persistence.ts:46](file:///F:/Codes/Git/Quantsmind-Products/QuantsMind-VSCode-AI-Coder/src/chat/persistence.ts#L46)).
- New v2 fields are all **optional**: `question`, `attachmentContext`, `localOnly`. Legacy records simply lack them and fall back to `text` replay (test "legacy records without a captured question replay their stored text").
- `attachments: string[]` (path labels) is still written on every message so an **older build can still read a v2 transcript** — downgrade safety, documented in `StoredMessage`.
- The storage key `quantsmind.chat.conversations.v1` is **unchanged**, so existing user conversations stay in place and existing provider settings/credentials remain valid — no re-entry of API keys is required.
- Unreadable records are quarantined to a separate key rather than deleted (§8).
- Migration is exercised by 11 unit tests, starting with "reads pre-0.3.4 records without a schema marker and upgrades them on write".

## 11. Security changes (assignment §7 — E and §9)

**No security mechanism was added, removed or relaxed.** Workspace trust, workspace containment, file-access restrictions, the approval/apply flow, SecretStorage protection, API-key redaction and the extension permission set are byte-for-byte unchanged in behaviour (verified by the unchanged lint-clean compile and the pre-existing security tests still passing).

New diagnostics are strictly size/count/identifier based:

- `request context id=… provider=… model=… mode=… stream=… messages=… systemChars=… historyMessages=… historyChars=… promptChars=… attachmentItems=… attachmentChars=… totalChars=… capturedAttachments=… capturedChars=… dropped=…` — [chatViewProvider.ts:1784+](file:///F:/Codes/Git/Quantsmind-Products/QuantsMind-VSCode-AI-Coder/src/chat/chatViewProvider.ts#L1784)
- `completion start provider=… model=… messages=… chars=… systemChars=… messageChars=… stream=… timeoutMs=…` — [src/providers/completionService.ts:108](file:///F:/Codes/Git/Quantsmind-Products/QuantsMind-VSCode-AI-Coder/src/providers/completionService.ts#L108); success `durationMs/chars/finishReason` (L123) and failure `code/status/retryable/durationMs` (L131) are unchanged.
- No prompt text, no attachment content, no file content, no API key, no `Authorization` header and no raw credential is written to any log line. `formatRequestBreakdown()` is unit-asserted to contain sizes only, to be a single line, and **not** to contain the system or prompt text. The `Logger` still redacts every line and prefixes an ISO timestamp (which supplies the required request timestamp).
- Stored attachment content is the **already-redacted** context block produced by `ContextService` (`redactions` is recorded per attachment), never the raw file. Redacted captures are excluded from the freshness audit so secret-bearing blocks are not re-read.
- Freshness-audit paths are validated by `resolveStoredPath()`: absolute paths, drive-letter paths, `..` and empty segments are rejected, so persisted metadata cannot make the extension read outside the workspace.
- Provider errors and context-restoration errors are distinguishable: provider failures are reported through the existing normalized `code/status/retryable` channel; restoration problems surface as `notice level=warn` history/attachment messages and `attachment freshness audit` / `conversation history ready` log lines. Test "reports provider failures without exposing credentials or request content" drives a 429 whose upstream body echoes the API key and asserts neither the key nor the prompt appears in the log or the notice.

## 17. Known limitations (reported honestly per §13)

1. **Native modal confirmations are not exercised by automated tests.** `vscode.window` and `vscode.commands` are getter-only inside the extension host, so the Clear/Delete confirmation dialogs cannot be driven headlessly. The *behaviour* is covered: provider-level `ConversationStore.clear()` isolation is unit-tested (test 17) and deleting one conversation never removing siblings (test 23). The dialog itself is **code-reviewed only**, not executed.
2. **No real DOM rendering proof.** The webview is validated by static HTML/CSP assertions plus the `getElementById` ↔ `id=` cross-check (test 29). Actual pixel rendering, click behaviour and the history-status strip in a live VS Code window were **not** observed by me — the user must confirm the UI in a running window.
3. **No live provider call for v0.3.4.** All automated provider evidence comes from a local mock HTTP server (by design — §8 forbids unnecessary live calls and credit spend). The **OpenRouter live retest carried over from Campaign 6 (send `Reply with exactly: READY` in a fresh chat and confirm the exact reply) is still unconfirmed**; it needs two clicks in a running VS Code window.
4. **The freshness audit is bounded**: last 12 captures per conversation, unredacted only, size-limited. Older or redacted captures are reported as `skipped=`, not as verified.
5. **Budget release is lossy by design**: past 24,000 chars/attachment-message, 50 attachments/message or 96,000 chars/conversation, the oldest captured content is dropped and honestly labelled — the original content is not recoverable, only the path label and the `ATTACHMENT_DROPPED_MARKER`.
6. **Replay does not re-read files.** Modified-on-disk files are warned about, and the older captured context is still what gets replayed — that is the intended semantics (§4: never substitute new contents for old captured context), but users may expect the opposite and should read the notice.
7. **Campaign 5 follow-up remains open**: `docs/reports/V033_WEBVIEW_RUNTIME_DIAGNOSIS.md` still lists four UI observations that only the user can perform.
