## 1. Reported symptom

Selecting an existing conversation-history entry — for example `Reply with exactly: READY (11)` — in the chat panel's **Conversation history** dropdown ends in a completely new (empty) chat instead of showing that conversation. Related complaint: **Restore** does not display the conversation the user selected.

## 2. Reproduction steps (as reproduced from real evidence, not re-performed by me)

1. Have at least two stored conversations, one non-empty (the 11-message one) and one that New Chat created and left empty.
2. Open the QuantsMind chat view.
3. In the **Conversation history** `<select id="conversation-select">`, choose `…(11)`.
4. Observe the panel; then either re-open the dropdown (the first real row below the action row is a second, unlabeled `New chat`) or press the **Restore** button in the history row.
5. The panel now shows an empty chat and the store's active conversation id becomes the blank conversation.

I did not perform the UI steps (no native UI access). The sequence in steps 3–5 is reconstructed from the **real host log of the user's own window** (§4), which contains exactly this pattern, twice.

## 6. Root cause

**Primary (confirmed):** the history list contains a persisted **empty** conversation titled `New chat`, created by New Chat and never filtered out. Two consequences, both proven:

1. **Restore is not selection-driven.** `restorePreviousConversation()` resolves the target as `mostRecent(except the active id)`. Because `save()` stamps `updatedAt = now` and New Chat persists the blank record, that record is *always* the newest, so Restore deterministically switches to the empty conversation. The user's words — "Restore does not display the selected conversation" — are exactly this. The blank conversation is then `setActive`d and becomes the restored view on the next window open (`source=reload transcriptMessages=0`), which is why the state persists.
2. **The blank record is indistinguishable from the "New chat" action.** `renderConversationSelect()` appends the count suffix only when `messageCount > 0`, so the stored 0-message conversation renders as plain `New chat`, as the first conversation row, immediately under the synthetic `New chat` action option. Any interaction that lands there performs a genuine `switchConversation` into a blank transcript — indistinguishable from "navigated to a completely new chat". Both observed 0-message switches are consistent with this (or with cause 1).

**Proven NOT to be the cause** (each ruled out by direct evidence):

- **Conversation-id propagation** — the (11) id reached the host, resolved, and loaded 11 turns twice.
- **Persistence** — all three records intact; `schema=2` written correctly on the two records v0.3.4 saved; the older 19-message record still readable (migration works on real data).
- **Transcript reconstruction / provider-session identity** — `providerMessages=11 providerChars=734` matches the stored record; `session.load()` is idempotent and correctly keyed by conversation id.
- **Switching being blocked** — the `busy` guard and `requestSeq` invalidation did not fire (no warning notices logged).
- **Attachment replay / freshness audit** — `attachmentTurns=0 unavailableAttachments=0` on both switches; these records hold no captured context, and no audit notice was emitted.

**Not proven (see §10):** whether the 0-message switch came from the duplicate `New chat` dropdown row (cause 2) or from the Restore button (cause 1) — both emit the identical log line and both resolve to the same record. This does not change the diagnosis; it is a combination of **Restore command wiring + history-list content/labelling**, i.e. UI/UX + wiring, not persistence or reconstruction.

## 9. Recommended minimal fix (NOT implemented — read-only assignment)

> **Addendum (same day, 2026-11-04):** items 1–3 below were subsequently implemented after this report was delivered, together with the regression tests listed in §8 (items 1, 2 and 3). §11's read-only statement describes the investigation phase only and does not cover that follow-up work.

Ordered by risk; all three are small and local.

1. **Stop surfacing empty records as history entries** — filter in the presentation boundary, not in the store, so no user data is deleted (this assignment's safety rules forbid removing the blank record):
   `postConversations()` ([chatViewProvider.ts:551](file:///F:/Codes/Git/Quantsmind-Products/QuantsMind-VSCode-AI-Coder/src/chat/chatViewProvider.ts#L551)) → `this.deps.conversations.list().filter((entry) => entry.messageCount > 0 || entry.id === this.conversation?.id)`; and in `renderConversationSelect()` ([media/chat.js:259](file:///F:/Codes/Git/Quantsmind-Products/QuantsMind-VSCode-AI-Coder/media/chat.js#L259)) render an active-but-empty record as e.g. `New chat — current, empty` so it can never be confused with the action row.
2. **Make Restore selection-aware** — accept the selected id: webview posts `{ type: 'restorePreviousConversation', id: els.conversationSelect.value }`; extend [protocol.ts:271-275](file:///F:/Codes/Git/Quantsmind-Products/QuantsMind-VSCode-AI-Coder/src/chat/protocol.ts#L271) (currently a no-payload case) with the existing `isId(record.id)` validation; in `restorePreviousConversation(id?: string)` ([chatViewProvider.ts:711](file:///F:/Codes/Git/Quantsmind-Products/QuantsMind-VSCode-AI-Coder/src/chat/chatViewProvider.ts#L711)) switch to `id` when supplied and only then fall back to `mostRecent(except active)`.
3. **Don't let an empty record win recency** — skip the `updatedAt` stamp (or skip persisting) for a conversation with 0 messages in `ConversationStore.save()` ([persistence.ts:213-224](file:///F:/Codes/Git/Quantsmind-Products/QuantsMind-VSCode-AI-Coder/src/chat/persistence.ts#L213)), which removes the deterministic "Restore → blank chat" outcome even before fix 2 lands.

Also worth adding: set `els.conversationSelect.value = state.activeConversationId || ''` **after** the rebuild in `renderConversationSelect()` instead of relying on `option.selected = true` set before `append()` — defensive, removes any dependence on implicit first-option selection in the `<select>`. (Same pattern exists in v0.3.3, so it is a hardening step, not the regression.)

Explicitly **not** recommended here: deleting the user's blank record, clearing globalState, or any storage migration — the observed data must be preserved.
