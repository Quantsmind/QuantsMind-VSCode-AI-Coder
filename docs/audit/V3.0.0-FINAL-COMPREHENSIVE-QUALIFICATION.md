## 4. Non-functional qualification

### 4.1 Reliability
- Failure isolation: tool/provider errors never terminate the extension host; MCP stdin EPIPE
  funneled through one rejection (QM-GA-029); illegal engine transitions emit a diagnostic
  (QM-GA-024).
- Recovery: checkpoint restore re-hashes applied files; refuses silent replay
  (`agentOrchestrator` restore tests); partial undo stays explicitly `partial`+retryable (QM-GA-025/N4).
- Cancellation: engine/orchestrator/service sink all paths to cooperative cancellation
  (`cancellation.ts`, signal-aware sleep, cancel-all). Pause semantics at step boundaries; restore
  is never automatic (documented).
- State consistency: apply/undo/prune paths are
  idempotent-ish and always leave the history store consistent; interrupted writes are marked
  failed, not resumed.
- Resource management/leaks: execution service bounds history (50); sessions capped; backups
  bounded (50-entry history + prune); timers signal-aware and cleared at every terminal path reviewed.

### 4.2 Performance (measured, this environment)
Machine: Windows host, Node 24.18.1 (exec tools) — tests executed via the repo toolchain's own
test runner; VS Code 1.95.0 pinned for integration.
- Unit suite (1,322 tests): ~1m 0s wall.
- Integration suite (124 tests, extension host + loopback mock): ~30–38s.
- Packaged-host suite (4 tests): ~3–13s.
- SSE event cap 1 MB; tool output cap 100k chars; request content cap 2,000,000 chars; index
  cap 5,000 files — all enforced and unit-tested, unbounded growth not possible on these paths.
- Activation overhead not separately benchmarked; `onStartupFinished` defers work until idle,
  status-bar only. No blocking I/O in activation path beyond constructing services (index is lazy).
*Honest limit: no CPU/memory profiling of the GUI was performed in this environment.*

### 4.3 Scalability
- Large repositories: index/retrieval caps (`maxIndexedFiles`, `retrievalMaxChars`) bound work;
  progress is reported; caches bounded. Very large monorepos will be truncated by design.
- Many MCP servers: ≤10 tracked; one client per server; oversized messages/capabilities rejected.
- Long conversations: 200 messages/120k chars/30 conversations cap; session events capped.
- Concurrency: single task at a time per session; executions deduplicated per cwd (win32-case-insensitive).

### 4.4 Maintainability
- Type-strict `tsc` build (`noImplicitAny`, `exactOptionalPropertyTypes`-adjacent posture via
  tsconfig); zero direct-`vscode` unit-test leaks; lint 0 errors (38 pre-existing `no-explicit-any`
  warnings, none in changed files, unchanged baseline since v2.5.7).
- Dead code eliminated in this pass (dead command registration removed; dead harness path guarded).
- God-class debt: `ChatViewProvider` (~2,533 lines; `handleMessage` 46 cases) — documented as
  P3/DEBT with no GA impact; refactoring is out of scope for a release-critical build.
- Heuristic, not compiler-grade: language intelligence is file-inventory + lexical relationships;
  docs now state this (`docs/LANGUAGE_INTELLIGENCE.md` unchanged, consistent with src).

### 4.5 Compatibility
- Engines: VS Code `^1.95.0` (tested ceiling 1.95.0; newer compatible by engine range).
- Node for development: `.nvmrc` pins 22; CI tests 20/22/24 on Linux and 22 on Windows/macOS.
  `package.json` deliberately declares no `engines.node` (the extension ships no Node-native
  dependencies; `minimatch` is pure JS). `.nvmrc` wins any local recommendation ambiguity.
- OS: Windows path verified; Linux/macOS unrun locally; CI lineage green on both (§11).
- Not supported and correctly not claimed: Web, Virtual Workspaces, Remote (manifest
  `virtualWorkspaces:false`; no browser target).

### 4.6 Usability & accessibility
- Command discoverability: all contributed commands visible except hidden `Show Menu`
  (status-bar backed, intentional); docs now list all 22.
- Approval/denial flows: modal flows with exact-operation-set checks; rejection paths produce
  honest outcomes, never silent success.
- Error recovery: error messages include actionable guidance; diagnostics distinguish permission
  vs absence (QM-GA-023). Screen-reader completeness is **not audited** — recorded honestly as an
  untested non-functional property with a requirement-to-fix owner decision.
- Settings docs: all 28 settings documented (this pass).

### 4.7 Privacy
- No telemetry, backend, database, or update service; zero runtime dependencies other than
  `minimatch`; local persistence bounded; redaction at every model-facing boundary (QM-GA-004..006,
  verified by test and review); workspace data never leaves the machine except configured provider/MCP endpoints;
  conversations persist locally under caps; backups under global storage (bounded retention).
- `redact.ts` removes configured and well-formed secrets; remnants risk is low but non-zero
  for arbitrary provider echoes; the untrusted-output framing is a second line of defense.
