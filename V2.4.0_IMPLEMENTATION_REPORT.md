## 2. What was implemented and where

### WP1 — Git repository intelligence
- `src/git/gitService.ts` (new): `isGitRepository`, `repoInfo` (root, bare state, branch, HEAD SHA/short, default remote), `status()` with porcelain v1 -z parsing (staged/modified/unstaged/untracked/deleted/renamed/conflict states), `log`, `branchList`, `remoteList` with credential stripping, in-progress detection (merge, rebase, conflicts via MERGE_HEAD / rebase-merge, status), `isClean`, Windows/POSIX path handling, spaces-safe argument arrays, bounded output, no shell.
- `src/agent/gitTools.ts` (new) wires those into the agent as read-only and approval-gated tools.

### WP2 — Diff and change review
- Working-tree and staged diffs, numstat, binary file detection, whitespace-error detection, truncation guard — all in `src/git/gitService.ts`.
- The existing `get_change_diff` agent tool continues to show agent-proposed diffs; git diffs flow through the same review UI.

### WP3 — Checkpoints and recovery
- `src/git/checkpointService.ts` (new): bounded in-memory checkpoints bound to task IDs.
- `create`/`createFromFs`/`list`/`get`/`restore` with:
  - conflict detection (diverging user edits are never overwritten),
  - clear restore result: `restored`, `alreadyIntact`, `conflicts`, `missingFiles`,
  - task-scoped `clearTask()`, duplicate/change-protection.
- Agent tools `create_checkpoint` / `restore_checkpoint` / `list_checkpoints`.

### WP4 — Change approval and rollback
- Existing `ChangeTools` + approval modal + `ChangeService` unchanged; Git and checkpoint tools reuse the same approval surface (no second change engine).
- Per-file and per-operation approval recorded through the same `approval` callback channel the rest of the agent uses.

### WP5 — Branch management
- `git_branch_list` / `git_create_branch` / `git_switch_branch` / `git_delete_branch`.
- `git createBranch` refuses invalid names; checkout-only branches print status; deletions use `-d` by default, `-D` requires explicit `force: true` plus approval.
- Switch refuses uncommitted-change conflicts at the CLI level and reports them clearly.

### WP6 — Commit preparation
- `git_stage` / `git_unstage` with explicit file lists only (`git add .`, `-a`, `*` refused).
- `git_commit` requires approval; stages reported back in the approval detail; returns SHA via `git rev-parse HEAD`.

### WP7 — GitHub integration
- `src/github/githubService.ts` (new): thin REST client with injected `FetchFn` for tests.
- `parseRemote()` handles `https://…` and `git@…:owner/repo.git` forms.
- `listIssues` / `createIssue` / `listPullRequests` / `getPullRequest` / `createPullRequest` — all against the `origin` remote, with token from `vscode.authentication.getSession('github', ['repo', 'read:user'], { createIfNone: false })`.
- Errors mapped to `unauthenticated | forbidden | rate-limited | not-found | validation | network | unknown`; the token is never included in any error message; the token never appears in agent output.

### WP8 — Webview integration
- Repository inspector now renders a **Git status** section: branch, HEAD, remote, staged/modified/untracked/deleted counts, changed file list, `in_progress` flags (merge/rebase/conflicts), recent commits, checkpoints.
- A GitHub section appears only when connected (issues/PRs). All rendered data stays local.
- Button `Git status` in the workspace row; CSP unchanged.

### WP9 — Safety
- All mutating operations (`stage`, `unstage`, `commit`, `create_branch`, `switch_branch`, `delete_branch`, `restore_checkpoint`, issue/PR creation) require approval.
- Never performs `git add .`, never force-pushes, never hard-resets, never cleans, never merges, never auto-commits.
- Explicit staging only; empty message refused; broad patterns refused.

### WP11 — Multi-language coverage

## 7. What is explicitly not done / honest limitations

- No integration, push, merge, release or publish behaviour exists in this milestone. The approval system gates every mutation.
- Git repositories nested inside the workspace are detected only via the root; submodule-aware operations are not supported.
- Checkpoint persistence is in-memory only; checkpoints do not survive window reloads.
- The GitHub integration was exercised against a controlled mock fixture (local HTTP server). It has **not** been run against real GitHub credentials in this environment.
- Branch deletion is limited to `-d` unless `force: true` is explicitly passed.
- No automated test executes against real GitHub; all GitHub tests use injected fetch fixtures.
- The webview is verified at the unit/render level (24/24 DOM-shim checks) rather than end-to-end inside a running VS Code window.
